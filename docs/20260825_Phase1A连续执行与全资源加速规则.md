# 2026-08-25 Phase 1A 连续执行与全资源加速规则

## 1. 本阶段完成定义

本阶段不是“启动了若干进程”，而是冻结矩阵中的 16 个 cell 全部达到：

1. 64 个优化器步骤完成；
2. adapter 保存、重载和哈希核验通过；
3. GSM8K 1319 条完整；
4. formal v5 独立审计通过；
5. SVAMP 300 条、ASDiv numeric 2067 条和 MultiArith 155 条完整；
6. OOD v3 独立审计通过；
7. 单格证据包及 SHA-256 生成；
8. 16/16 前不输出准确率、不比较方法、不修改冻结参数。

只有 16/16 `AUDITED_PASS` 才进入统一解盲和预注册统计。

## 2. 用户授权后的连续执行规则

早期运行手册禁止自动启动下一格，是为了避免未经人工验收直接扩散错误。2026-08-25 用户明确要求在保持逐格审计的前提下连续执行。因此增加外层控制器：

`scripts/run_budget_equivalent_phase1_continuous.py`

它不修改冻结矩阵，只把原有单格命令串成以下有限状态机：

`训练/重载/GSM8K -> formal audit -> OOD -> OOD audit -> 证据包 -> 下一格`

任何一步失败且在限定重试次数内无法按原目录恢复，控制器立即停止，不跳过、不创建第二个正式 run、不提前解盲。

## 3. 加速边界

允许且已经采用：

- GSM8K 沿用冻结的两个评估 worker；
- OOD 使用两个并发通道：ASDiv 长通道，以及 SVAMP 后接 MultiArith 的短通道；
- 每个 OOD 数据集仍保持 `shard_count=1` 和物理 batch size 1；
- CPU 同时承担 tokenizer、数据校验、parser 重算、SHA 和打包；
- 内存用于模型加载和 Linux page cache，保留冻结的最低空闲内存；
- 显存允许装载两个独立评估 worker，但每个 worker 仍受 13 GiB 峰值上限约束；
- GPU 每五分钟记录温度、利用率、显存和功耗；达到冻结的 80°C 硬停止线即安全终止当前进程组，冷却后从原断点恢复。

禁止：

- 修改模型、LoRA、训练步数、监督词元预算、prompt、parser 或 selector；
- 把 OOD 单 worker 的 batch size 从 1 改大；
- 把运行到一半的任务改成不同 shard 数；
- 为提高表面占用率无意义地填满 CPU、内存或显存；
- 同时训练两个正式 cell；
- 在 16/16 前读取、汇总或输出准确率。

## 4. 为什么评估比训练慢

每格训练虽然有 1000 次样本曝光，但被合并成 64 个优化器步骤，且训练回答长度受到 32K 监督词元预算约束。评估需要逐题自回归生成：GSM8K 1319 条，三套 OOD 共 2522 条，每个新词元都依赖前面已经生成的词元。冻结协议又要求物理 batch size 1，所以总生成时长显著高于训练是合理的，并不说明训练“太少”。训练量是否需要升级属于 Phase 3 的预算泛化问题，不能在当前 Phase 1A 中临时增加。

## 5. 当前进一步提速的优先级

1. 立即采用两通道 OOD 并发，减少 GPU 等待 CPU/tokenizer 的空隙；
2. 使用连续控制器消除 cell 之间的人工等待和 GPU 空转；
3. CPU 归档和哈希尽量安排在 GPU 加载或下一格准备期间；
4. 完成本轮后再用完整 canary 比较 4090D 与 5090 的“每个审计通过 cell 成本”，不能在冻结矩阵中临时换 backend；
5. 后续新矩阵可预注册批量 generation、离线 tokenization、长度分桶和更高 physical batch，但当前矩阵不改。

资源利用的目标是缩短每个 `AUDITED_PASS` cell 的墙钟时间和成本，同时保持输出等价与可恢复性，不是让每个硬件指标长期显示 100%。
